# Mesh402 Render deployment

## Boundary: two funding models

The operator demo invokes the existing agent CLI with the operator's payer and
Tripo credentials. Only `/demo/live` and `/demo/operator/state` require the
operator session. Login is `POST /demo/operator/session`; session cookies last
one hour, are HttpOnly, SameSite=Strict, and Secure on HTTPS. The credential is
entered at `/operator`, sent in a POST body, and never bundled or placed in URLs.
The gate limits login attempts and compares hashed credentials in constant time.
Origin checking is a separate CSRF protection, not the authorization boundary.

Public `/health`, replay evidence, the optimized GLB, registered delivered GLBs,
and sanitized task receipts remain unauthenticated. Unregistered asset IDs return
404. Raw `generated/` content is never a static directory.

The independent caller-funded `POST /api/v1/generate` now uses its own x402
payment boundary. It does not require an operator session or use the operator
payer. It is disabled by default and has a persistent quota. See
[PUBLIC-API.md](PUBLIC-API.md) for contract, caller signing, configuration and the
separately authorized real-test sequence. The golden payment service remains
loopback-only inside the operator CLI.

## Runtime

One paid Render Node Web Service, one instance. Node 22.23.2 (see `.node-version`).
Production entry point: `server/start.ts`; static root: `dist-visual` only.
The handler is reused by local Vite through `frontend/dev-bridge.ts`.
Golden `src/agent`, `src/x402`, `src/tripo`, and the existing CLI are unchanged.
No runtime package or auth framework was added. `tsx` is an existing runtime
requirement, so retain dev dependencies in the install command below.

Build: `npm ci --include=dev && npm run typecheck && npm run build:visual`
Start: `npm start`
Health: `GET /health` → `{"status":"ok"}`
Listen: `0.0.0.0:$PORT` (Render supplies PORT).
Working directory: repository root.
Persistent disk: `/opt/render/project/src/generated`.

Only the paid service capability and a persistent disk are required. Select the
paid instance size and disk capacity in Render; no price/plan is hardcoded here.
Start with capacity for the intended number of roughly 42 MB live assets, receipts,
and disk headroom. Disks cannot be attached to free services, shared across
instances, or used during build. Disk services have downtime on deployment:
https://render.com/docs/disks

## Configuration

Set in Render Environment (never in Vite client variables):

| Variable | Value |
| --- | --- |
| NODE_ENV | production |
| PUBLIC_ORIGIN | Exact `https://<service>.onrender.com` origin, no trailing slash |
| MESH402_UI_EXECUTION | dry-run |
| LIVE_OPERATOR_SECRET | New random secret generated by the operator; not the local test credential |
| NEBIUS_API_KEY | Existing server-side key |
| NEBIUS_BASE_URL | https://api.tokenfactory.nebius.com/v1 |
| NEBIUS_MODEL | Qwen/Qwen3-235B-A22B-Instruct-2507 |
| TRIPO_API_KEY | Existing server-side key (unused in dry-run) |
| HEDERA_PAYER_ACCOUNT_ID | Existing testnet payer account |
| HEDERA_PAYER_PRIVATE_KEY | Existing ECDSA testnet key (unused in dry-run) |
| HEDERA_PAY_TO_ACCOUNT_ID | Existing testnet recipient |

The credentials' presence never enables paid mode. Missing operator secret closes
the gate. A local `.env.local` is optionally loaded by the start command, remains
ignored, and is not shipped. Render injects environment variables directly.
Public replay works with no provider credentials and without the forensic source.

## Storage, recovery and receipts

The packaged replay is `frontend/public/assets/replay/manifest.json` and its
optimized GLB; build copies them into `dist-visual`. No Tripo signed URL is needed.
`/demo/receipt` returns this immutable replay manifest.

`generated/wrapper/<mode>.lock` is atomically created before invoking the CLI.
It is never automatically deleted. Separate dry-run/live locks allow an explicitly
approved mode change after dry-run validation without turning a dry-run result
into paid evidence. One attempt per mode persists across browser reload, process
restart and deployment. Concurrent claims cannot start two children.
`<mode>-state.json` records progress and completion. Interrupted running state, or
a lock without state, becomes `ambiguous` after restart. The operator can read
`/demo/operator/state`; no automatic payment or generation retry exists.

`generated/wrapper/registry.json` persists only approved public asset metadata.
After successful delivery, `/demo/assets/<taskId>.glb` and
`/demo/receipts/<taskId>.json` survive restarts. The inspector selects the matching
receipt URL. The original raw CLI receipt stays private; the wrapper preserves a
mode-specific full receipt separately. Dry-run uses the existing isolated cwd
`generated/ui-dry-run/`, so it cannot overwrite the accepted paid CLI receipt.

For another deliberate run, FIRST reconcile payment/task/receipt state manually.
Then archive the mode's lock and state files outside `wrapper/` using Render Shell
or SSH, restart, reauthorize, and explicitly confirm the next run. Never delete a
lock just because the browser lost its connection. Sessions expire on restart.
Do not edit the public asset registry casually or expose its raw filesystem.

The request remains an NDJSON stream, not a durable queue. Real CLI milestones
are forwarded; chamber scanning is a metaphor. A disconnect leaves the child
running. A process crash may leave a settled payment or remote Tripo task without
a locally delivered asset. Examine saved state/receipts/provider task before action.
A receipt lookup after reconnect is read-only; it never resumes a paid call.

Disable auto-deploy during demos. Avoid restarting while a run is active. Render
permits long HTTP responses, but client/network loss, provider timeout, disk-full,
memory pressure and service restart remain possible. There is no browser stream
reconnection or multi-instance execution coordinator. Large files consume egress
and browser GPU memory. Keep offline backups of original receipts and GLBs.

## Click-by-click: existing Render project “Mesh402”

1. Sign in to Render and select the workspace containing **Mesh402**.
2. Open **Projects → Mesh402**, select the intended environment, then **New → Web
   Service** (or create a Web Service and assign Project = Mesh402 in the form).
3. Choose **Git Provider → GitHub**, grant repository access if needed, and select
   **ValenteCreativo/mesh402**. Do not create a Static Site or Background Worker.
4. Set branch **main**, runtime **Node**, and leave **Root Directory blank**.
5. Enter build command `npm ci --include=dev && npm run typecheck && npm run build:visual`.
6. Enter start command `npm start`.
7. Choose a **paid** instance that supports persistent disks. Select capacity based
   on the memory/disk needs above; this guide makes no pricing commitment.
8. Under **Advanced → Add Disk**, set mount path
   `/opt/render/project/src/generated` and choose the desired disk capacity.
9. Add the Environment values above. Keep `MESH402_UI_EXECUTION=dry-run`.
   Use the assigned service URL as PUBLIC_ORIGIN; if not yet shown, set it to the
   actual assigned URL before testing operator login, then redeploy.
10. Set **Health Check Path** to `/health`. Use manual deployment during validation.
11. Click **Create Web Service**. Confirm build/start logs, healthy status and URL.
12. Open `/health`, then `/`: verify public replay, derivative asset, receipt, and
    GLB download. Check it with provider services unavailable/credentials absent
    before relying on replay as a fallback.
13. Confirm unauthenticated `POST /demo/live` returns 401. Open `/operator`, enter
    the operator secret, return to LIVE and perform only the authorized **dry-run**.
    Confirm no payment/generation and inspect `/demo/operator/state`.
14. Restart after completion, reauthorize, and verify the attempt remains locked
    while replay and previously registered assets remain accessible.
15. STOP. Do not enable paid LIVE or run another generation without explicit approval.

Current Render form terminology may vary slightly. Official setup reference:
https://render.com/docs/web-services

## Verification commands (non-spending)

```
npm run typecheck
npm run test:wrapper
npm run test:agent:guards
npm run build:visual
npm start
```

The existing `test:tripo`, `test:x402`, `test:e2e` and agent `--live` commands spend
credits or submit payments. They are NOT deployment tests and must not run here.
Backend safety checks use the existing mocked agent guard suite; the production
wrapper suite covers access boundaries, registry and crash/restart behavior.
